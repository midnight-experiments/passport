# The `sol_ed25519` arm: a Solana wallet as a Passport device and grantee

A Passport account can be controlled by a Solana wallet: Phantom, or any wallet whose `signMessage` produces an RFC 8032 Ed25519 signature over the raw bytes it is given. The wallet needs no SOL and sends no Solana transaction. It signs one readable message per operation, and the contract renders that message itself from the values it executes on.

Source: `contracts/account-sol-ed25519.compact` (included by `account.compact`), client facade `src/wallet/signer-sol-ed25519.ts`, independent message renderer `src/wallet/sol-ed25519-message.ts`. Status of this document: the grammar and the acceptance policy of format `sol v1`, kept correct in place while the arm is in development (no format versions before release); the measurement report and the full circuit set are completed with the remaining operations.

## 1. Acceptance policy

Each rule is listed with every layer that enforces it. "Decoding" is the honest proof server's input check: it was exercised (the evidence labels it `decoding`), but a malicious prover does not run it, so it is never counted as a constraint. "Circuit constraint" names what the proof itself enforces; where the source is a static reading of the crates the pinned proof server builds with (proof server 9.0.0-rc.8 pins midnight-zkir 3.1.0-rc.1 and midnight-circuits 7.2.4), it says so: no honest proof server lets such an input reach the circuit, so these constraints are not exercised by a prover test.

| Rule | Client | Runtime (generated JavaScript) | Proof server decoding (exercised) | Circuit constraint |
|---|---|---|---|---|
| Strict RFC 8032 decoding of the 32-byte key: canonical `y < p`, on the curve, no "negative zero" | `parseSolanaPublicKey` | — (the circuits take a `Curve25519Point`, never key bytes) | — | — |
| `A` in the prime-order subgroup (small-order and mixed-order keys) | `parseSolanaPublicKey` (torsion check) | the `Curve25519Point` type check | refused (S2, S5) | yes (static reading): a `Curve25519Point` input is assigned by `ForeignEdwardsEccChip::assign`, which witnesses a point `Q`, asserts it is on the curve and returns `[8]Q` (midnight-circuits 7.2.4, `ecc/foreign/edwards_chip.rs`), so every point input lies in the prime-order subgroup; a prover choosing a torsion `Q` gets `O`, which `A ≠ O` refuses |
| `A ≠ O` | yes | the assert | — | `require_live_sol_ed25519_key` at activation; the standard library's `ed25519Verify` on every verification |
| `R` canonical and in the prime-order subgroup | `decodeSolSignature` | the point type | refused (S5) | as for `A` (static reading) |
| `R ≠ O` | yes | the assert | — | the seam's explicit assert (exercised: refused at the prover, S5); `ed25519Verify` does not refuse it |
| `s < L` (an `S + L` twin is refused, never reduced) | `decodeSolSignature` | the `Curve25519Scalar` type | a non-canonical scalar encoding is refused (S5) | the circuit's `s` is an element of the scalar field: `S + L` would be the same value, so the twin is the same input, and it could only re-authorise the exact message the wallet signed, which the single-use entry and the nonce refuse to replay |
| Cofactorless verification, no ZIP-215 relaxations | the pre-check: noble `{ zip215: false }`, which is **cofactored** (`[8][s]B = [8]R + [8][k]A`), run only after the explicit canonicity and torsion checks on `A` and `R` above; on torsion-free `A` and `R` the cofactored and cofactorless equations accept the same signatures, so the pre-check equals the circuit's rule. noble alone is not the policy: AA 00067 audit G1(S) measured it accepting 64 of 64 signatures under a mixed-order key, where OpenSSL accepted 6 | — | — | `ed25519Verify<#n>`: `[s]B == R + [k]A`, `k = SHA-512(R ‖ A ‖ msg) mod L` |
| A coordinate outside the field | — | the type check and the value encoder | — | the canonical decomposition of the next row |
| One point, one 32-byte key | — | — | QA-1: a non-canonical limb encoding of a coordinate is refused (S5, `decoding`) | yes (static reading): the key bytes are `curve25519PointY(pk) as Bytes<32>` plus the parity of `x`; the cast (ZKIR `into_coordinates`, then `to_bytes`) is `assigned_to_le_bytes(…, Some(32))`, which decomposes with `enforce_canonical = true` and asserts canonicity for 255 bits (midnight-circuits 7.2.4, `field/foreign/field_chip.rs`). The decomposition is unique, so a point has exactly one 32-byte key in the circuit, whatever limbs a prover supplies. Uniqueness rests on this constraint, not on the decoding refusal |
| One `Field`, one 32-byte rendering (the recovery key's coordinates and the backup vector values, AA 00067 G1S-6) | `solRecoverySession` refuses a value at or above the field modulus `r` before any signature | the cast is canonical and the display check compares the nibbles with it | an approval over the rendering `f + r`, signed with matching nibbles, is refused by the display check (S9, prover) | yes, exercised against a dishonest witness: compactc lowers `f as Bytes<32>` to ZKIR `div_mod_power_of_two(f, 248)`, which midnight-zkir 3.1.0-rc.1 synthesises as `assigned_to_le_bits(f, None, enforce_canonical = true)`; over 255 bits that ties bit 0 to `sgn0(f)`, and `f + r` (the only other 255-bit representation) has the other bit 0. A MockProver run of that gadget with the decomposition witness replaced by the bits of `f + r` is unsatisfiable; with `enforce_canonical = false` it is satisfied and renders `f + r` (S9 evidence `qa-s3/`). So a value has exactly one rendering, and no range assert is needed |

Independent oracle (spec FR-012, FR-018): Node's OpenSSL Ed25519 (cofactorless), and noble with `{ zip215: false }` plus the explicit checks above (`src/tests/sol-ed25519-offline.ts`).

**Wallets that cannot enrol.** The client signs nothing it has not pre-checked: the wallet's signature must verify, cofactorless, over exactly the bytes the circuit renders. A Phantom account backed by a Ledger signs through the Ledger Solana app, which signs a message only inside the Solana off-chain message envelope (`0xff "solana offchain"` header) or not at all; its signature is over other bytes, so the pre-check refuses it at the first step (the blind request, section 2) and such an account cannot enrol as a `sol_ed25519` device. Use a software Phantom account, or a Ledger through an arm that signs hashes (`k256`). Measuring this with a real Ledger is part of the live-wallet step, and what Phantom actually displays for a `sol v1` message is still to be checked by a person (both PENDING-OWNER).

## 2. Identity and the blind

The device is the wallet's public key `A`, carried as a `Curve25519Point` and related in-circuit to the 32-byte RFC 8032 encoding the wallet exports (`encode_public_key_with_sol_ed25519`: `y` little-endian, the low bit of `x` in bit 255). Entries, boot commitments and grant ids bind those 32 bytes and the account's blind:

```
blind    = SHA-256(pad32("midnight:account:blind:sol:v1") || signature(64))
entry    = SHA-256(pad32("midnight:account:device:sol:v1") || account || key || blind || le4(epoch) || le8(counter))
boot     = SHA-256(pad32("midnight:account:boot:sol:v1") || salt || key || blind)
grant id = SHA-256(pad32("midnight:account:grant:id:sol:v1") || account || key || blind || origin_hash || le1(slot))
```

The blind's signature is the wallet's `signMessage` over the readable request message of `src/wallet/blind.ts` (Midnight Passport, the network, the wallet's base58 key, the account index, and a warning that the signature reveals the account's privacy key). Enrolment signs it twice and refuses a wallet whose two signatures differ (`deriveSolBlind`). No circuit accepts the request message as an authorisation: its first line differs from every operation's.

`compute_public_key_with_sol_ed25519(seed)` derives the point and its 32 bytes from an RFC 8032 seed with the contract's own arithmetic (SHA-512, clamp, reduction mod `L`, `[s]B`), for software signers and tests. There is no raw-scalar helper.

## 3. The signed message, format `sol v1`

```
Midnight Passport approval (sol v1)        circuit-fixed first line: the format and its version
Operation: <title>                         fixed per circuit
Site: <label>                              the site's words (32 bytes), marked as the site's
Role: device of this account               or "Role: grantee of a scoped grant"
Account: <64 hex>                          the account's contract address
Signing key: <64 hex>                      the signer's 32-byte Ed25519 key
<operation lines>                          every operand and consumed witness value, in full
Consequence: <...>                         fixed, on authority-granting operations
Device nonce: <20>                         device role: auth_nonce
Grant label: <32> / Grant slot: <3> /      grantee role: the grant's identity and freshness
Grant issued at nonce: <20> / Grant use nonce: <20>
```

Rules:

- Printable ASCII and LF only; no final LF. Every line starts with text the circuit fixes.
- Numbers are decimal, left-aligned and space-padded to their type's full width (`Uint<8>` 3, `Uint<32>` 10, `Uint<64>` 20, `Uint<128>` 39), so each layout has one fixed length. The digits are display inputs that the circuit checks against the value: for each value exactly one text is valid.
- Bytes are lowercase hex, two digits per byte, in full. Curve coordinates and Field values are shown in the one order every arm and the base's comparison display use (`COORDINATE_DISPLAY_ORDER` in `src/wallet/descriptors.ts`; AA 00067 decisions Q29 and Q33): secp256k1 and P-256 coordinates big-endian, as SEC1 and their wallets show them; JubJub coordinates little-endian, Midnight's own encoding and the bytes the entries bind; Field values (the recovery session's backup vector) little-endian.
- The site chooses two texts, and the circuit marks both as the site's: the label after `Site: ` (visible words separated by single spaces), and, on a moved amount, the decimal point and symbol after `This site labels it: ` (0 to 18 decimals, a symbol of 1 to 8 visible characters whose first is a letter, so the symbol never reads as more digits of the number, as in `1 000`; the digits are the amount's). Neither can contain a line break, so neither can start a line, and neither moves value.
- Enumerated values are shown as circuit-fixed words, each selected by the value and refused for any other value: the recipient kind (`any recipient`, `unshielded user address`, `shielded coin public key`, `contract address`) and a `k256` key's signing envelope (`SHA-256 of the challenge`, `dApp-connector signData`), both from the base's rendering module (`recipient_kind_text`, `k256_envelope_text`, the same texts as the EVM arm's and the client's `labels.ts`), and the operation flags and the caller restriction (`yes`, `no`).
- No digest, fingerprint or truncation. The only hash-like values ever shown are the four listed in the spec, each under its fixed label: a `k256`/`jubjub` grantee's origin hash (`Grantee site label (hash)`), a passkey's RP hash (`Passkey RP (hash)`), a target's or a grantee's blind (`Device privacy salt`, `Grantee privacy salt`: a grantee's blind comes from its own request naming the issuing account, AA 00067 Q39, never from a device request), and the literal entry of a revocation-only removal (`Removes a device this wallet cannot identify` / `Device entry`).
- Another key (`add_device`, `remove_device`, `issue_grant`, `revoke_grant`) is a readable descriptor: its registered tag as text, then its key: an EVM address and a passkey origin in the form their own wallets show; a Solana key as its 32 bytes in 64 hex digits (its wallet shows base58, see section 4); `k256`, `jubjub` and passkey keys as coordinates in the order above. Every class renders into one fixed-length block (padded with spaces before its last line break), and the circuit derives the entry or grant id from exactly those values; a field a class does not use must be zero, so two targets never render the same bytes.

### Display inputs

Compact has no division, and turning bytes into characters costs about 140 rows per byte in-circuit, so the caller supplies every text the circuit cannot cheaply derive, and the circuit **checks** each against the value it describes (spec Q30):

- decimal digits (left-aligned, space-padded): read back to the value;
- the site's amount label: its digits read back to the amount;
- hex: two arguments per message. `frame` holds the nibbles of the account and the signing key: the seam checks them against `kernel.self()` and the key it derives from the point the signature is verified under. `hex` holds the nibbles of every other value the message shows in hex. Both are high nibble first, each value in its stored byte order (curve coordinates little-endian, Field values as their canonical 32-byte little-endian encoding); the circuit assembles the bytes from them, asserts they equal the value, and makes each digit with one comparison;
- characters of the site label, a grant label and a passkey origin: assembled and compared with the bytes (the site label is only text; its shape is checked).

The seam (`require_authorised_with_sol_ed25519`) renders the common frame itself: the first line, the account (`kernel.self()`), the signing key (derived from the point the signature is verified under), and the freshness tail (`auth_nonce`, or the grant's label, slot, issue nonce and use nonce). A gated circuit passes it only its circuit-fixed title and the body it renders from its operands, so no circuit can pass an identity, an account, a nonce or a frame of its own (AA 00067 audit G1(E), G1E-1).

For each value exactly one input is valid, so the inputs add no freedom. `src/wallet/sol-ed25519-message.ts` builds all of them (`solShow`, `solAmountShow`, `nibblesOf(...solDeviceHexValues(...))`, …).

### Never a Solana transaction or off-chain message (spec FR-S03)

Every message starts with `Midn` (bytes 77, 105, 100, 110).

- As a legacy transaction message, that is a header (77, 105, 100) followed by a key count of 110, so a parse needs at least 3 + 1 + 110 × 32 + 32 + 1 = **3,557 bytes**. The longest message is 1,673 bytes. The bound is tight: an independent parser of the wire format accepts a `Midn` buffer of exactly 3,557 bytes and refuses one of 3,556 (`src/tests/sol-ed25519-message-offline.ts`).
- Even at that length, such a message never passes Solana's sanitize rules: its header claims 105 read-only signed accounts out of 77 required signatures, so there is no writable fee payer.
- The first byte is below `0x80`, so it is not a versioned message, and it is not `0xff`, so it is not the off-chain message envelope (`0xff "solana offchain"`).
- As a signed transaction it would carry 77 signatures (4,928 bytes).
- No message contains the Sign-In With Solana statement.

`assertSafeSolMessage` checks every message before any wallet is asked. The frozen corpus (`src/tests/vectors/sol-ed25519-messages-v1.json`) holds the contract's circuits and the independent renderer to each other byte for byte.

## 4. What a person can check by eye (spec FR-022)

- **Comparable with what the other wallet shows**: an EVM address (`0x` and 40 lowercase hex digits; the wallet shows the same digits, mixed-case by EIP-55), a passkey origin (its exact text), the amounts in base units and the site's labels as text.
- **Shown in full, but not comparable by eye with the wallet**: a Solana key, shown as 64 hex digits while Phantom and Solana explorers show base58 (this includes the `Signing key` line, the signer's own key); `k256`, `jubjub` and passkey keys (coordinates); the account address; tokens, nonces and ciphertexts. For a new device or a grantee, the check is the comparison display: the new device's own client renders the identical descriptor (with the Solana key in base58 beside its hex form, `describeDescriptor` in `src/wallet/descriptors.ts`), and the user compares the two screens (spec FR-023, Q18). A base58 rendering checked in-circuit is possible later (two display limbs) and is not part of `sol v1`.

A Solana target of `add_device`, `remove_device`, `issue_grant` and `revoke_grant` (another device or a grantee) is also carried as a `Curve25519Point`, as the signing device is (AA 00067 Q37): the gated circuits take it beside the descriptor (`target_pk`, `grantee_pk`; every other class passes the identity, its unused point) and require the 32 bytes the message shows and the entry or grant id binds to equal the point's encoding, derived in-circuit with the same function the seam uses, which refuses the identity (`A ≠ O`); the point type admits only the prime-order subgroup (section 1). So a target can only ever be a usable key, and the key a user enrols is the key that later signs. The client decodes the wallet's 32 bytes strictly first (`parseSolanaPublicKey`). (The point is a separate argument because compactc 0.35.0 aborts on a `Curve25519Point` field in an exported struct.)

## 5. Networks (spec FR-015)

An approval names no network: no `sol v1` layout carries a network value, and the contract holds none (decision Q4). It binds the account address (`Account:`), the role and operation, the operands, the signer's key and the freshness state (`auth_nonce`, or the grant's nonce). An account can be cloned onto another network at the same address, and an approval for it would then authorise the same call there, if the clone reached the same `auth_nonce` with the same device entry. No in-contract value could tell the clone apart: a sealed value is copied with the clone, and circuits cannot read the network id. Clients make the case unlikely by deploying with random nonces (the address depends on them), and the residual is the ledger's: binding the network id, which the upstream ledger issue proposes. The full argument is completed with the MIP text. The network named in the blind request (section 2) is a client convention that gives each network its own blind; no circuit checks it, so it does not bind an approval to a network.

## 6. Recovery (the recovery MIP, sections 5 and 6)

`publish_recovery_session_with_sol_ed25519` and `recover_cancel_with_sol_ed25519` pass the device seam (over `auth_nonce`, section 3) and then call the shared chips unchanged: `do_publish_recovery_session` (no recovery pending; a vector of 1 to 4 values with the unused slots zero; a fresh, non-zero session identifier; a fresh recovery key that is not the identity and has no small order) and `do_recover_cancel` (something pending). The recovery gate itself, `recover_submit` and `recover_finalise`, is upstream's and does not depend on the arm.

The session's approval shows every operand in full under the consequence line `Consequence: sets this account's recovery key; its holder can take over this account after the veto window.`: the new recovery key's two JubJub coordinates and the four backup vector values as 64 hex digits each, little-endian (section 3), the session identifier, the vector length in decimal, and the 64-byte key wrap in two lines (1,250 bytes). The cancel shows the frame and `Consequence: the pending recovery of this account is cancelled.` (391 bytes). Each `Field` has exactly one rendering (section 1, the last row).

Finalisation clears every device entry (upstream #183), so after a recovery every old `sol_ed25519` device is refused by membership, including an entry an upstream arm's raw `add_device` planted at `device_epoch + 1` before the recovery: without the clear, that plant would be live at the new epoch. This arm's own `add_device` enrols only at the current epoch and counter 0 (section 3). The successor, a JubJub device, enrols new devices, and a fresh `sol_ed25519` device can then publish a new session.
