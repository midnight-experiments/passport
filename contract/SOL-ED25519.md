# The `sol_ed25519` arm: a Solana wallet as a Passport device and grantee

A Passport account can be controlled by a Solana wallet: Phantom, or any wallet whose `signMessage` produces an RFC 8032 Ed25519 signature over the raw bytes it is given. The wallet needs no SOL and sends no Solana transaction. It signs one readable message per operation, and the contract renders that message itself from the values it executes on.

Source: `contracts/account-sol-ed25519.compact` (included by `account.compact`), client facade `src/wallet/signer-sol-ed25519.ts`, independent message renderer `src/wallet/sol-ed25519-message.ts`. Status of this document: the grammar and the acceptance policy are frozen (2026/10/15, format `sol v1`); the measurement report and the full circuit set are completed with the remaining operations.

## 1. Acceptance policy

| Rule | Where it is enforced |
|---|---|
| A strict RFC 8032 decoding of the 32-byte key: canonical `y < p`, on the curve, no "negative zero" | client (`parseSolanaPublicKey`); the circuit never takes key bytes, it takes a `Curve25519Point` |
| `A` in the prime-order subgroup (small-order and mixed-order keys refused) | client; runtime (the `Curve25519Point` type check); prover (ZKIR `FromCoordinates` is unsatisfiable outside the subgroup) |
| `A ≠ O` | client; circuit (`require_live_sol_ed25519_key` at activation; the standard library's `ed25519Verify` on every verification) |
| `R` canonical and in the prime-order subgroup | client (`decodeSolSignature`); runtime and prover (the point type) |
| `R ≠ O` | client; circuit (the seam's explicit assert; `ed25519Verify` does not refuse it) |
| `s < L` (an `S + L` twin is refused, never reduced) | client; runtime and prover (the `Curve25519Scalar` type) |
| Cofactorless verification, no ZIP-215 relaxations | circuit (`ed25519Verify<#n>`: `[s]B == R + [k]A`); client pre-check with noble `{ zip215: false }` |
| A coordinate outside the field | runtime (type check and value encoder); never a proof input |

Independent oracle (spec FR-012, FR-018): Node's OpenSSL Ed25519 and noble with `{ zip215: false }` plus the explicit checks above (`src/tests/sol-ed25519-offline.ts`).

## 2. Identity and the blind

The device is the wallet's public key `A`, carried as a `Curve25519Point` and related in-circuit to the 32-byte RFC 8032 encoding the wallet exports (`encode_public_key_with_sol_ed25519`: `y` little-endian, the low bit of `x` in bit 255). Entries, boot commitments and grant ids bind those 32 bytes and the account's blind:

```
blind    = SHA-256(pad32("midnight:account:blind:sol:v1") || signature(64))
entry    = SHA-256(pad32("midnight:account:device:sol:v1") || account || key || blind || le4(epoch) || le8(counter))
boot     = SHA-256(pad32("midnight:account:boot:sol:v1") || salt || key || blind)
grant id = SHA-256(pad32("midnight:account:grant:id:sol:v1") || account || key || blind || origin_hash || le1(slot))
```

The blind's signature is the wallet's `signMessage` over the readable request message of `src/wallet/blind.ts` (Midnight Passport, the network, the wallet's base58 key, the account index, and a warning that the signature reveals the account's privacy key). Enrolment signs it twice and refuses a wallet whose two signatures differ (`deriveSolBlind`). No circuit accepts the request message as an authorisation: its first line differs from every operation's.

`compute_public_key_with_sol_ed25519(seed)` derives the point and its 32 bytes from an RFC 8032 seed with the contract's own arithmetic (SHA-512, clamp, reduction mod `L`, `[s]B`), for software signers and tests. There is no raw-scalar helper.

## 3. The signed message, format `sol v1`

```
Midnight Passport approval (sol v1)        circuit-fixed first line: the format and its version
Operation: <title>                         fixed per circuit
Site: <label>                              the site's words (32 bytes), marked as the site's
Role: device of this account               or "Role: grantee of a scoped grant"
Account: <64 hex>                          the account's contract address
Signing key: <64 hex>                      the signer's 32-byte Ed25519 key
<operation lines>                          every operand and consumed witness value, in full
Consequence: <...>                         fixed, on authority-granting operations
Device nonce: <20>                         device role: auth_nonce
Grant label: <32> / Grant slot: <3> /      grantee role: the grant's identity and freshness
Grant issued at nonce: <20> / Grant use nonce: <20>
```

Rules:

- Printable ASCII and LF only; no final LF. Every line starts with text the circuit fixes.
- Numbers are decimal, left-aligned and space-padded to their type's full width (`Uint<8>` 3, `Uint<32>` 10, `Uint<64>` 20, `Uint<128>` 39), so each layout has one fixed length. The digits are display inputs that the circuit checks against the value: for each value exactly one text is valid.
- Bytes are lowercase hex, two digits per byte, in full. Curve coordinates and Field values are shown in the one order every arm and the base's comparison display use (`COORDINATE_DISPLAY_ORDER` in `src/wallet/descriptors.ts`; AA 00067 decisions Q29 and Q33): secp256k1 and P-256 coordinates big-endian, as SEC1 and their wallets show them; JubJub coordinates little-endian, Midnight's own encoding and the bytes the entries bind; Field values (the recovery session's backup vector) little-endian.
- The site chooses two texts, and the circuit marks both as the site's: the label after `Site: ` (visible words separated by single spaces), and, on a moved amount, the decimal point and symbol after `This site labels it: ` (0 to 18 decimals, a symbol of 1 to 8 visible characters; the digits are the amount's). Neither can contain a line break, so neither can start a line, and neither moves value.
- No digest, fingerprint or truncation. The only hash-like values ever shown are the four listed in the spec, each under its fixed label: a `k256`/`jubjub` grantee's origin hash (`Grantee site label (hash)`), a passkey's RP hash (`Passkey RP (hash)`), a target's blind (`Device privacy salt`), and the literal entry of a revocation-only removal (`Removes a device this wallet cannot identify` / `Device entry`).
- Another key (`add_device`, `remove_device`, `issue_grant`, `revoke_grant`) is a readable descriptor: its registered tag as text, then its key in the form its own wallet shows (an EVM address, a 32-byte Solana key, a passkey origin) or its coordinates in the order above. Every class renders into one fixed-length block (padded with spaces before its last line break), and the circuit derives the entry or grant id from exactly those values.

### Display inputs

Compact has no division, and turning bytes into characters costs about 140 rows per byte in-circuit, so the caller supplies every text the circuit cannot cheaply derive, and the circuit **checks** each against the value it describes (spec Q30):

- decimal digits (left-aligned, space-padded): read back to the value;
- the site's amount label: its digits read back to the amount;
- hex: one argument per message, `hex`, the nibbles of every value the message shows in hex (high nibble first, each value in its stored byte order: curve coordinates little-endian, Field values as their canonical 32-byte little-endian encoding); the circuit assembles the bytes from them, asserts they equal the value, and makes each digit with one comparison;
- characters of the site label, a grant label and a passkey origin: assembled and compared with the bytes (the site label is only text; its shape is checked).

For each value exactly one input is valid, so the inputs add no freedom. `src/wallet/sol-ed25519-message.ts` builds all of them (`solShow`, `solAmountShow`, `nibblesOf(...solDeviceHexValues(...))`, …).

### Never a Solana transaction or off-chain message (spec FR-S03)

Every message starts with `Midn` (bytes 77, 105, 100, 110).

- As a legacy transaction message, that is a header (77, 105, 100) followed by a key count of 110, so a parse needs at least 3 + 1 + 110 × 32 + 32 + 1 = **3,557 bytes**. The longest message is 1,646 bytes. The bound is tight: an independent parser of the wire format accepts a `Midn` buffer of exactly 3,557 bytes and refuses one of 3,556 (`src/tests/sol-ed25519-message-offline.ts`).
- Even at that length, such a message never passes Solana's sanitize rules: its header claims 105 read-only signed accounts out of 77 required signatures, so there is no writable fee payer.
- The first byte is below `0x80`, so it is not a versioned message, and it is not `0xff`, so it is not the off-chain message envelope (`0xff "solana offchain"`).
- As a signed transaction it would carry 77 signatures (4,928 bytes).
- No message contains the Sign-In With Solana statement.

`assertSafeSolMessage` checks every message before any wallet is asked. The frozen corpus (`src/tests/vectors/sol-ed25519-messages-v1.json`) holds the contract's circuits and the independent renderer to each other byte for byte.
